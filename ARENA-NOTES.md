# Arena notes: candidate 1

The skill now does three things it did not before. It explains its own report: a Needs attention list, expectations per shot, coverage of every changed file, numbered close-ups, a swipe view, and provenance. It turns "page shows errors" into "page shows realistic data" with one command that drafts typed mocks from the project's own types. And it loads cleanly in Claude Code, Codex, pi and Grok, which I checked with each harness's own loader. The existing capture, diff, circled and report output is unchanged; I checked that byte for byte against the original script.

### Mocking (goal 2)

| Change | Reason |
| --- | --- |
| `unanswered.json`: one entry per endpoint with method, origin, path, reasons, example URLs, request body and shots. It covers fetch, XHR, EventSource and WebSocket calls that failed, were blocked, returned 404 or 5xx, or got the dev server's HTML fallback page. Same-origin calls are keyed by path, since the ports differ. | The old output printed only `METHOD path (reason)` for fetch and XHR, so WebSocket failures and HTML-fallback answers went unnoticed (the fixture's live badge silently stayed hidden). |
| `mocks.mjs draft <report-dir> --project <tsconfig>`: for each endpoint it finds the calling code with the project's own TypeScript compiler and reads the response type, from a type argument (`get<T>()`) or the function's return type, unwrapping `Promise` and `{ data }` wrappers. It works for JSDoc JavaScript too. It matches URL literals, templates with resolved constant prefixes, concatenations, and constant identifiers passed to client calls. The HTTP method at the call site breaks ties. GraphQL is matched by operation name, and WebSocket messages are typed from the subscribe callback's parameter. Tests, globs, JSX links and navigation calls are ignored. It then builds deterministic, plausible, fictional values from field names. | Fact 2: writing four mocks took several manual steps (run, read unanswered calls, find DTOs, hand-write JSON). On Greyhoundster's real code, the draft typed all four of the owner's endpoints from the actual DTOs in about 3.5 s. It even got the maintenance gate right (`enabled: false`) and reproduced the `numberOf*` field names the owner typed by hand. |
| `mocks.mjs find` (call sites, types and fixture mentions for one URL), `sample <Type>` (a value for per-state variants), and `serve` (the same mock file over real HTTP on the pinned API port). | `find` and `sample` cover the manual remainder. `serve` handles frameworks that fetch on the server (Next.js, Remix, Nuxt, SvelteKit), which in-browser routing cannot reach. |
| New mock features: `query`, `graphql`, `requestJson`, `requestText`, `resourceTypes` matchers; `sse`, `image`, `handler` (stateful per capture of each side), and `websocket` with `send`/`onMessage` responses; mock files listed in `mocks`; `name`/`note`. | "Think beyond simple REST": GraphQL, WebSocket, SSE, CDNs, stateful flows such as POST-then-list, and variants by query or body. |
| **WebSocket guard for `allowHosts`** (`routeWebSocket` closes disallowed hosts and passes the frontend's own host through). | A probe showed `context.route('**/*')` never sees WebSocket upgrades, so `allowHosts: []` did not stop WebSockets from reaching production. The own-host pass-through (HMR) was tested with a real echo server. |
| `serviceWorkers: "block"` by default. | A probe showed that with service workers allowed, a worker answers `/api/answer` itself and the Playwright mock is bypassed. Greyhoundster ships a PWA service worker (`dev-dist/`). |
| Data mocks never answer documents, scripts, styles, images or fonts, and the report names any mock that matched such a request. | Fact 4: `**/api/**` matched `/src/app/api/*.ts` and broke the app. Reproduced with `/src/api/client.js` in the fixture: the module still loads, and the report says to pin the mock. |
| `placeholderImages`, `initScripts` (for stubbing SDK globals, listed in the report), `contextOptions` (geolocation, permissions). | Blocked CDN images and missing third-party globals were the remaining ways a mocked page looked broken. |
| A quiet-network wait that ignores `pending` mocks, EventSource and WebSocket. It replaces `networkidle`. | Capturing a loading state used to need a per-shot `networkIdleTimeoutMs` workaround; now it works by default. |

## Alternatives considered and rejected

- **A faker or json-schema-faker dependency for mock values.** Rejected: it adds dependencies to the tool cache and nondeterminism. The small name-aware generator is deterministic, so drafts are reproducible and both sides match.
- **Bundling TypeScript in the tool cache.** Rejected: setup would modify a shared cache and pull about 20 MB, and a project with types already has a compiler (version-matched). Resolution order: `UI_CHANGELOG_TYPESCRIPT`, the project's `node_modules` and its parents, the tool cache. Without one, the draft falls back to a text search.
- **Generating MSW handlers inside the project.** Rejected: the skill must not modify the project under review. Browser-level routing does the same job from outside.
- **OCR or model-written change descriptions in the report.** Rejected: nondeterministic and heavy. The agent writes the summary after looking at the close-ups.
- **Separate close-up PNG files.** Rejected in favour of CSS crops of the existing PNGs: no extra files, and the full images stay one click away. `report.md` keeps the full before, after and circled images for PRs.
- **Blink and onion-skin modes.** Only swipe was added; one extra interaction is enough, and it handles differing sizes.
- **Claude Code-only frontmatter** (`allowed-tools` with `${CLAUDE_SKILL_DIR}`, `argument-hint`, `when_to_use`, `disable-model-invocation`). Rejected under the portability requirement: Grok spells `when-to-use` differently, `${CLAUDE_SKILL_DIR}` is literal text elsewhere, and claude.ai packaging rejects unknown keys.
- **Installing into `~/.agents/skills` as well.** Rejected: Codex and pi read both locations, so the skill would be listed twice. I verified that the existing installer paths load in all four harnesses.
- **Full Socket.IO emulation.** Rejected as too much code for its value. It is documented as a `handler` recipe and marked untested.
- **A shared fixture folder under `evals/`.** Rejected because the eval runner may try to load it as a case. Each case carries its own copy of the small fixture site.
- **Recording HARs from a disposable backend.** Deferred: the two-sided semantics (record on which side, and when to refresh) need a design, and HAR replay already works.

### How portability was checked

- Read each harness's current rules: pi's installed `docs/skills.md` (Agent Skills spec; name at most 64 characters, description at most 1024), Codex's "Build skills" page via the OpenAI docs server (`name` and `description` required, descriptions shortened when many skills are installed, so front-load the use case), Grok's built-in documentation from its binary (no xAI page covered the CLI; `metadata` values must be strings), and the Claude Code docs in the grounding.
- `tests/check-portability.mjs` runs each installed harness's own loader against the skill, with a throwaway home so no configuration is touched:
  - `claude plugin validate skills/` with `CLAUDE_CONFIG_DIR` set to a temp folder;
  - `codex debug prompt-input` with `CODEX_HOME` set to a temp folder containing a symlink to the skill (the skill appears in Codex's skills list with its description);
  - `grok inspect --json` with `GROK_HOME` set to a temp folder (the skill is listed with its full description);
  - pi's own `loadSkillsFromDir` from its installed package (loaded, no diagnostics).
- Static checks in the same script: frontmatter parses with the strict `yaml` package pi uses, only spec fields appear, name, description and compatibility limits hold, metadata values are strings, `SKILL.md` is under 500 lines, and no harness-specific tool names or substitutions (`Read tool`, `${CLAUDE_SKILL_DIR}`, `$ARGUMENTS`) appear in `SKILL.md` or the references. Every file `SKILL.md` names exists, scripts import only `node:` built-ins and their own files, and every script passes `bash -n` or `node --check`.
- `~/.claude.json` and `~/.codex/config.toml` had the same modification times before and after the check.
- The scripts need only Node (22.12 or newer) and bash; the browser tools come from `setup.sh`, and TypeScript is optional and comes from the project.
- The eval `prompt.md` settings blocks name Claude Code tools in `allowed_tools`. That block is `claude plugin eval` run configuration, which the skill-creator template requires verbatim; it is not skill content, and other harnesses ignore it.

## Open problems

- **Close-up before boxes are approximate** when columns shift by different amounts and a region spans several of them: the box is the union of the mapped bands. The report links the full images, and `troubleshooting.md` says so.
- **Draft heuristics have limits.** Generic `request(path)` wrappers called with computed paths, GraphQL documents imported from `.graphql` files, and zod-inferred types without declared return types can leave `TODO` entries or pick a near miss; the note always names the call site it used. Values are plausible but domain-neutral (Greyhoundster dog names need an edit), and booleans that gate whole screens still need a review.
- **Server-side rendering**: `mocks.mjs serve` skips WebSocket mocks, and per-shot variants cannot reach server-side fetches.
- **Third-party SDK stubs** (maps, payments) remain hand-written `initScripts`.
- **Polling apps** still make each settle wait the full `networkIdleTimeoutMs` cap.
- **Route hints** assume formatted code (indentation) and do not follow route objects spread from other files.
- **`evals/trigger-queries.json`** sits next to the case folders. I assume `claude plugin eval` ignores files that are not case folders; that is untested.
- **`unanswered.json`** also lists third-party calls blocked by `allowHosts` (analytics, for example). The draft creates `TODO` mocks for them, which the agent should delete when they do not affect the screen.
- **Errors present on both sides** are not flagged (only errors new on the after side are), and for unchanged shots they appear only in `results.json`, because unchanged shots get no row. Pre-existing errors are not the change's fault, but a reviewer may still want a count.
